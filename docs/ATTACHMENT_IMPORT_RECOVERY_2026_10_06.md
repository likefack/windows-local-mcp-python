# 添付取り込みの実接続調査と復旧（2026-10-06）

## 調査で分かったこと

利用者が添付したJPEGを `artifact_import_file` へ渡すと、クライアントは
`INVALID_ARGUMENT` と汎用エラーだけを返した。フォルダー一覧・通常の読み取りも同様に失敗した。

監査の読み取りによって、通常操作の内部エラーは
`ApprovedHostAuthorityUnavailable: CreateFileW(Approved Host authority pipe) failed: WinError 2`
と分かった。既存 `WindowsLocalMCPApprovedHost` サービスが停止していた。
添付取り込みはこの共通確認より先に進めず、元画像の大きさやBase64上限が原因との証拠はない。

運用Pythonでは `annotated_types` を読み込めず、依存関係検査も失敗した。
不足していたのは、導入済み版と照合して以下の5依存だった。

- `annotated-types==0.8.0`
- `anyio==4.15.1`
- `attrs==26.1.0`
- `cffi==2.1.1`
- `click==8.5.0`

SCMイベント7009・7000は04:40:21 JSTの起動タイムアウトを記録した。
サービスのDispatcher接続前に依存を読み込む実装と、依存欠落による起動失敗は整合する。
サービス実装自体の開発版・運用版SHA-256は一致していた。

配備時のログは5依存の導入成功と `pip check` 成功を記録し、配備後一覧にも5件が存在する。
`runtime` と `site-packages` の最終更新時刻は04:19:24 JSTで、配備完了04:04:03より後だった。
導入後に依存ファイルが失われた可能性が高いが、削除した操作・実行主体は未特定である。
初期の配備漏れ、利用者の操作、別作業などのいずれかを断定しない。

## 復旧と保全

管理者確認を経て、処理中・承認待ち操作と回復状態がないことを確認し、同じ版の5依存だけを復元した。
稼働中プロセスが使用する `_cffi_backend` は上書きせず、展開先と一致することを確認したうえで
欠けたファイルだけを排他的に追加した。復旧前から存在していた `site-packages` の全対象ファイルが
復旧後も同じSHA-256であることを検査した。既存cffi補助実行ファイルも保持した。

`pip check`、全依存の版の一致、サービスモジュールの読み込みを確認し、04:49:40 JSTまでに
サービスが `Running` へ復帰した。実接続のフォルダー一覧取得も成功した
（operation_id: `6998a084-ee4e-4314-9102-cec97de016e6`）。
設定、ワークスペース、資格情報、監査データ、承認・回復状態、ACL・所有者はこの復旧で変更していない。
安全性確認を無効化して操作を通す変更も行っていない。

最初の直接pip復元は使用中の既存cffiファイルへの書き込みで停止し、一部の不足ファイルだけを復元した。
その後、別フォルダーへ展開して既存同一ファイルを保持する復旧へ切り替えた。
最終確認コマンドのWindows PowerShellによる引用符の扱いも修正して再実行した。

## 添付参照と追加した診断

サービス復旧後、同じ画像の実接続呼び出しは `ATTACHMENT_IMPORT_NOT_CONFIGURED` を返した
（operation_id: `048dec30-5d7d-46e9-b023-dee0100c5c7d`）。
このコードに到達するには、参照がURLとファイルIDを含むオブジェクトへ変換され、形式検査を通過する必要がある。
クライアント向け定義が文字列だからfileParams変換が失敗している、という当初の疑いはこの結果では支持されない。
初回の汎用 `INVALID_ARGUMENT` と、復旧後の許可ホスト未設定は区別する。

許可ホスト未設定の応答には、実際の参照から得た検証済みDNSホスト名だけを追加した。
URLのパス、署名クエリ、ファイルID、元ファイル名は返さない。監査は従来の汎用的な未設定理由を保ち、
ホスト名も永続化しない。表示されたホストを自動許可せず、既存の正確なホストへの限定取得を維持する。
公開引数・fileParams定義・既存保存と復旧の境界は変更していない。

添付取り込みの既存3テストファイルと新規診断テストは **83 passed in 10.02s**。
ネットワーク応答は合成であり、実ChatGPT添付の取得成功をこの結果だけで主張しない。
運用版は現在の導入済み内容を基準に、`attachment_import.py` と `server.py` の診断部分だけを反映した。
リポジトリにある別作業の未コミット変更は配備していない。

証拠と復旧用一式: `.dev-tmp/attachment-repair-20261006/`。
署名URL・ファイルIDはこの文書に記録しない。

## 実画像の取り込み成功

新しい診断を実接続で使用し、配信ホストが `sdmntprkoreacentral.oaiusercontent.com` と分かった。
OpenAI公式の[ネットワーク案内](https://help.openai.com/ja-jp/articles/9247338-network-recommendations-for-chatgpt-errors-on-web-and-apps)
は `oaiusercontent.com` 配下をOpenAIの利用ドメインとして挙げている。これは広いネットワーク設定の案内であり、
個別ホストや会話所属の独立証明ではない。今回の実添付参照で観測した正確なホスト1件だけを
`attachment_import_allowed_hosts` へ追加した。ワイルドカードやドメイン全体を許可していない。
設定変更は元設定のSHA-256一致を前提とし、このキー以外の設定が変わっていないことを検査した。
元設定は同じ設定ディレクトリの `config.before-attachment-host-20261006.toml` に保存した。

配備後の接続確認では一時的にTunnel未接続になり、通常ランチャーを既存設定で再起動した。
終了原因を断定しない。許可ホスト設定追加後は、対象設定に属するMCPサーバーのPID・起動時刻・
コマンドハッシュを照合し、処理中操作がないことを確認して設定を再読み込みさせた。
再接続中の1呼び出しは129.3秒でタイムアウトし、監査操作に到達せず画像も作成されなかった。
その後の再試行が成功した。タイムアウトした呼び出しを成功例や転送所要時間に含めない。

- operation_id: `8d71a641-bd7f-484d-a849-839435ae95a1`
- 保存先: `C:\Users\22905\Personal_knowledge\attachment-import-test-20261006-yatte-motor.jpg`
- 元データ・保存後のサイズ: ともに198,917バイト。
- 元データ・保存後のSHA-256:
  `7e7db6c1cef25c7b09be23e6f84cec5f0f10a0471fc0f709f0a5884f7ca23148`
- `source_sha256_verified=true`、`rollback_state=complete`。
- 成功したツール呼び出し全体は10,331ms。クライアント・添付参照の準備・通信・保存の分離計測ではなく、
  他経路との最速比較を証明する値でもない。

サーバー結果とは別にPowerShell `Get-FileHash` で元添付と保存先を読み直し、ハッシュ一致を確認した。
今回の画像と接続における直接取り込み成功を確認したのであり、別地域の配信ホスト、
別クライアント、全形式や大容量ファイルまで実機確認したとは扱わない。
依存ファイルを失わせた操作は引き続き未特定で、再発原因の解決まで証明した意味ではない。

最終検査は復旧前から存在する2,587ファイルを照合し、レビュー済み診断2ファイル以外が
同じSHA-256であることを確認した。運用版の変更不能性検査も成功し、runtime digestは
`02bd3083fcd149760f7d7121251bc7da65fdf7fc0f93bfdca8661cad0517eda7`。
認証付きauthority接続は `ok=true`、`healthy=true`。これは保護状態と接続前検査の証拠であり、
Approved Hostの承認後実行や異常終了・回復の再検証ではない。
