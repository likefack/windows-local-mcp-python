# 複数クライアント・並行タスクの監査

同じ Windows 利用者が、同じ作業領域に複数の ChatGPT や MCP クライアントから接続し、
複数のタスクを進めるための仕組みです。操作は同じ Audit DB に保存し、接続とタスクを
識別する項目で追跡します。別ユーザー間の認証・アクセス分離を提供するものではありません。

## 使い方

1. 接続後に `session_info` を呼び、`session_id`、`origin_scope`、`workspace_root` を確認します。
2. 会話・作業ごとに短い `task_id` を決め、すべてのツール呼び出しに同じ値を付けます。
   例: `read_file(path="readme.md", task_id="docs-update")`。
3. 自分の履歴は `audit_list(session_id="返されたID", filter_task_id="docs-update")`、
   または `activity_timeline` の同じ引数で絞り込みます。
   `task_id` は今回の呼び出しのラベル、`filter_task_id` は閲覧する履歴の条件です。
4. 別接続へ引き継いだ作業は、`session_id` を省略して `filter_task_id` だけで検索できます。

`task_id` は省略可能で、ASCII 英数字から始まる80文字以内の英数字・`.`・`_`・`:`・`-`
を使用できます。秘密情報や会話本文を入れないでください。省略した呼び出しの `task_id` は
`null` です。直前の要求の値を接続全体の既定値として記憶しないため、同じ接続を共有する
複数会話でも、一方のラベルが他方へ移りません。MCP ツールの説明にもこの使い方を公開します。

## 記録する項目

| 項目 | 意味 |
| --- | --- |
| `session_id` | サーバーが接続に割り当てる監査用ID。MCPの認証情報やHTTPのセッショントークンとは別 |
| `server_instance_id` | サーバープロセスを識別するID。再起動時に変わる |
| `origin_scope` | `connection`: 接続、`request`: 要求単位、`process`: 通信外のローカル処理 |
| `client_name` / `client_version` | MCP クライアントが申告した名前・版。取得できなければ `null` |
| `request_id` | MCP の要求ID。通信外では `null` |
| `task_id` | 呼び出しごとに指定する作業ラベル。省略時は `null` |

接続が継続している間は同じ `session_id` を使用し、再接続には新しいIDを割り当てます。
通信方式が要求ごとに接続を作る場合はIDも要求ごとに変わります。接続情報を得られない
場合にも要求単位のIDを作り、複数の要求を同じ接続と推測しません。

ChatGPT の会話IDは推測・取得しません。中継が複数会話を1本の MCP 接続へまとめた場合、
サーバーだけでは会話を自動判別できないため、`task_id` で区別します。クライアント名と
タスク名は自己申告で、同じ値を指定すれば同じラベルになります。いずれも認可、承認、
操作の所有権、操作停止の権限を与える値ではありません。

## 監査と表示

新規操作には発行元を必ず記録します。通信外の処理にもプロセス単位のIDを付け、接続を
観測したかのようには表示しません。既存DBは列と検索用索引を追加して移行しますが、
過去の `session_id = null` の操作の発行元は復元できないため、推測で書き換えません。

操作作成時の発行元は以後変更しません。別クライアントによる転送チャンク・再試行等の
イベントには、その要求の発行元をイベント側の `origin` として保存します。既存イベントや
専用の内部SQLで生成する一部の承認・復旧イベントは `origin = null` のままです。
worker が操作の完了状態を更新しても、開始したクライアントの情報は保持します。

`audit_list`、`audit_get`、`activity_timeline`、`activity_get`、`operation_report` から
発行元を確認できます。絞り込みは件数上限の適用前に行い、接続とタスクの両方を指定した
場合は両条件に一致する操作を返します。引数を省略した一覧は従来どおり全接続を対象にします。
Activity Monitor と承認画面の Live Activity にも短い発行元表示を加えます。
表示時の伏せ字、制御文字除去、長さ制限、再接続端末の読み取り専用動作は維持します。

## 同時実行と起動時の復旧

別対象の処理は既存の対象別ロックで並行実行できます。同じ対象の処理、作業領域全体の
変更、Approved Host の監視などは、既存の競合検知・承認・排他条件に従います。
同じファイルの更新には `expected_sha256` などの既存の同時変更検知を使ってください。
発行元ラベルによってロック・上限・承認・復旧条件が緩和されることはありません。

実行待ちの作成と承認後の実行権取得では、監査DBの共通ロックとトランザクション内で
実行枠を確認します。起動前の失敗は実行待ちのまま残さず、後続タスクの枠を解放します。

別サーバーが起動しても、worker の情報をまだ持たない実行待ち・同期処理を誤って中断に
しないよう、実行開始を担当するプロセスの PID・作成時刻・実行ファイルを内部に保存します。
これは追跡用の `session_id` とは別の生存確認情報です。worker の情報が既にある場合は
従来のworker判定を優先します。起動時の復旧は作業領域のロック取得後に状態を読み直し、
ロックの待機期限切れだけを理由に実行中の記録を復旧不能へ変更しません。

## 適用と検証の範囲

変更したソースを使うサーバーでは次回起動時にDB移行が行われます。Program Files 配下の
運用runtimeを使う構成では、既存のruntime更新手順で更新し、Tunnel / MCP を再接続して
ツール定義を更新してください。ソースの変更だけでは起動中の運用runtimeへ反映されません。
運用環境の更新後は、通常の PowerShell で
`powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File .\setup-localmcp.ps1 -RefreshApprovedHostTunnel`
を実行すると、対話メニューなしで既存の接続設定を検証・更新できます。
Tunnel は事前に停止し、成功後に `run-localmcp.bat` で起動してください。
詳しくは [ローカル起動ランチャー](LOCAL_LAUNCHERS.md) を参照してください。

回帰試験は実 MCP SDK の独立接続、同一接続内の並行要求、要求別スレッドへの引き継ぎ、
監査DB移行、履歴の絞り込み、既存競合検知、起動時の生存確認を対象にします。
ChatGPT と Tunnel を通した本番の複数会話、Windows Sandbox / Approved Host の実機境界は
別途確認が必要です。これらの確認を自動テストの成功で代替しません。
